# Week 4 report: incident memory, risk routing and the approval API (agent system v2)

Locked by `src/week4_report.py`. Every number below is read from the dev runs, their comparison and the test logs; none was typed in. No model was called to write this report.

## 1. What was built

- **Case database** (PostgreSQL): versioned migrations 0001_core_schema, 0002_guards_and_audit, 0003_functions, 0004_roles_and_views; cases, alert references, verdicts, evidence, routing decisions, proposed containment actions, approval decisions, simulated executions and a hash-chained audit log; constraints, indexes and foreign keys; idempotent ingest; one-time approval transitions; least-privilege role. Migration checksums are in the lock record.
- **Incident memory**: a numpy (optionally ChromaDB) index of 1200 training incidents (label + numeric flow fingerprint only), seeded from the train split only, with a manifest and an allowlist.
- **Graph v2** (`v2.0`): the Week 3 graph plus one optional memory step, a memory on/off switch, and a memory-aware verdict prompt (`agent_v2_memory`) used only when memory is on. With memory off the Week 3 code path and prompt (`agent_v1`) run unchanged.
- **Risk routing** (`risk-policy-v1`, sha256 `c36b7083c232069af2dc39cd93d4b97cb5b624dfeec0033ea6a5c9a5a481ceae`): transparent rules decide auto_close / escalate / needs_review with stated reasons; memory can only raise caution; proposed actions come from the verdict alone.
- **Approval workflow**: proposed actions are 'pending' until an authorised approver approves or rejects them once; rejected or unapproved actions can never be executed; execution is simulated and recorded only. No real containment exists in the code.
- **Approval API** (FastAPI over a framework-free handler layer): cases, pending approvals, approve/reject with idempotency keys, decision history, memory provenance and evidence; authentication and role checks; dev-only open mode that only listens on loopback.

### Limitations and confounders

- One run per arm. The model is non-deterministic even at a fixed seed, so a difference between the arms mixes the effect of memory with run-to-run noise. The Week 2 Day 6 replicate spread shows how large that noise was for the baseline; no significance test is made or implied.
- Dev set only, one split of CIC-IDS2017. Attack flows from the same tool and the same attacker host recur across files, so training and dev flows can be near-duplicates in feature space even though no flow is shared. Memory can look helpful because of that regularity, which would not carry over to different traffic.
- Memory holds only training labels and a numeric flow fingerprint (decision D-W4-1): it cannot supply MITRE technique ids, so any change in technique accuracy comes through the model's attack-type reasoning, not through looked-up ids.
- The memory arm changes two things at once: it adds evidence (neighbour labels) and it uses a longer prompt (agent_v2_memory). They cannot be separated with these two runs.
- Routing thresholds are policy defaults fixed before the runs (config/risk_policy.json); none was tuned on dev or frozen data. Every dev alert is already a detector alert, so the share the policy auto-closes depends on how its detector-score ceiling sits against the detector threshold; read the auto-close and escalation rates as properties of this policy, not as a recommendation.
- Approvals are human decisions. The runs only propose actions; no approval rate is measured and nothing is executed.
- The frozen evaluation set was not used for tuning, seeding or threshold choice, and was not opened for this comparison.
